## English

### Context

PRs #36–#40 introduced new v0.3.0 boundaries for named profiles and installed launcher plugins. `basedpyright` was already a development dependency, but no configuration or CI step prevented those public/runtime boundaries from drifting back to implicit `Any`.

This increment makes typing an enforced gate without turning the entire legacy repository into an annotation-only refactor.

### Implemented changes

- Added a strict basedpyright configuration for the public launcher SDK, profile service, core launcher base, plugin discovery, plugin adapter, and launcher registry.
- Added `uv run basedpyright` to primary CI after Ruff and before provider contract tests.
- Added the same strict type-check step to complete release validation.
- Added structural Protocols for profile selection validation and launcher registry collaborators.
- Narrow stored profile dictionaries only after runtime object and string-key validation.
- Type installed launcher discovery with `importlib.metadata.EntryPoint` and a literal discovery-status type.
- Preserve explicit runtime validation of plugin metadata and capabilities while satisfying strict static checking.
- Mark SDK and core packages with PEP 561 `py.typed` markers.
- Verify those markers from isolated installed wheels in package and release smoke paths.
- Make release workflow path filters include the root `pyproject.toml`, where the strict type-check scope is configured.

### Strict scope

The first enforced strict scope intentionally covers v0.3.0 boundary code rather than unrelated legacy modules:

- `packages/sdk/src/modelctl_sdk/launcher.py`
- `packages/sdk/src/modelctl_sdk/__init__.py`
- `packages/core/src/modelctl_core/services/profile_service.py`
- `packages/core/src/modelctl_core/launcher/base.py`
- `packages/core/src/modelctl_core/launcher/discovery.py`
- `packages/core/src/modelctl_core/launcher/plugin_adapter.py`
- `packages/core/src/modelctl_core/launcher/registry.py`

New v0.3 boundary work should remain compatible with this gate; broader repository conversion can be evidence-driven later.

### Validation path

The first strict CI run surfaced missing PEP 561 markers plus real narrowing issues in plugin discovery and stored profile keys. These were fixed structurally rather than disabling strict diagnostics. A subsequent primary CI run reached zero basedpyright errors before release/package hardening was added.

### Deferred work

- Evidence-driven profile portability only if real usage demonstrates a need.
- Final v0.3.0 documentation and completion-criteria review.
- Dedicated readiness review and promotion of the exact validated `refac` lineage to `main`.

## 한국어

### 배경

PR #36–#40에서 named profile과 설치 launcher plugin을 위한 새로운 v0.3.0 경계가 추가되었습니다. `basedpyright`는 이미 개발 의존성에 있었지만, 공개 SDK와 runtime 경계가 다시 암묵적 `Any`로 흐르는 것을 막는 설정이나 CI gate는 없었습니다.

이번 increment는 전체 레거시 저장소를 annotation-only 리팩터링으로 바꾸지 않으면서 타입 검사를 실제 강제 gate로 만듭니다.

### 구현 변경 사항

- 공개 launcher SDK, profile service, core launcher base, plugin discovery, plugin adapter, launcher registry에 strict basedpyright 설정을 추가했습니다.
- Primary CI에서 Ruff 이후 provider contract 테스트 전에 `uv run basedpyright`를 실행합니다.
- Complete release validation에서도 동일한 strict type-check를 반복합니다.
- Profile selection validation과 launcher registry collaborator를 구조적 Protocol로 명시했습니다.
- 저장된 profile dictionary는 runtime object 및 string-key 검증 후에만 typed mapping으로 좁힙니다.
- 설치 launcher discovery에 `importlib.metadata.EntryPoint`와 literal discovery status 타입을 적용했습니다.
- Plugin metadata/capability의 runtime 검증은 유지하면서 strict static checking을 만족하도록 경계를 분리했습니다.
- SDK/core package에 PEP 561 `py.typed` marker를 추가했습니다.
- Package와 release smoke path에서 격리 설치된 wheel에 marker가 실제 포함되는지 검증합니다.
- Strict type-check 범위를 정의하는 root `pyproject.toml` 변경이 release workflow를 트리거하도록 path filter를 보강했습니다.

### Strict 범위

첫 강제 범위는 unrelated legacy module이 아니라 v0.3.0 경계 코드에 집중합니다.

- `packages/sdk/src/modelctl_sdk/launcher.py`
- `packages/sdk/src/modelctl_sdk/__init__.py`
- `packages/core/src/modelctl_core/services/profile_service.py`
- `packages/core/src/modelctl_core/launcher/base.py`
- `packages/core/src/modelctl_core/launcher/discovery.py`
- `packages/core/src/modelctl_core/launcher/plugin_adapter.py`
- `packages/core/src/modelctl_core/launcher/registry.py`

향후 v0.3 경계 코드는 이 gate를 계속 만족해야 하며, 저장소 전체 확대는 실제 필요에 따라 진행할 수 있습니다.

### 검증 경로

첫 strict CI 실행은 PEP 561 marker 부재와 plugin discovery/profile stored-key narrowing 문제를 실제로 검출했습니다. Strict 진단을 끄지 않고 구조적으로 수정했고, 이후 primary CI에서 basedpyright 0 error를 확인한 뒤 release/package 경로까지 강화했습니다.

### 후속 작업

- 실제 사용에서 필요성이 확인될 경우에만 profile portability 추가
- 최종 v0.3.0 문서 및 completion criteria 검토
