# PR #18 — Publish ready versions from trusted merged PR events

- Pull request: https://github.com/LEEBONGHAK/modelctl/pull/18
- Merged: 2026-08-03
- Base / head: `refac` ← `release/merged-pr-tagging`
- Merge commit: `e315b5e3e99cc6a45a143b2ce8965498532cee67`

## English

### Context

PR #17 declared version `0.1.0` ready and added publication after a trusted `refac` push. The connector-backed merge did not produce a visible push-triggered tag, so the release process needed another trusted GitHub event that could identify the exact merge commit without trusting a pull-request head branch.

### Changes

- Added the `pull_request: closed` release event.
- Required the pull request to be actually merged with base branch exactly `refac`.
- Skipped closed but unmerged pull requests.
- Checked out `pull_request.merge_commit_sha` for post-merge validation and publication.
- Reran dependency audit, Ruff, the complete test suite, package builds, installed-wheel smoke checks, and checksums against the merge commit.
- Granted `contents: write` only to the publication job after every release gate succeeded.
- Preserved immutable tag and GitHub Release behavior.
- Added workflow regression tests and bilingual trust-boundary documentation.

### Validation and outcome

The pull-request dry run, CI, Package, and Ubuntu, macOS, and Windows tests passed. After merge, repository branch inspection showed that the configured default branch was still `main`, while the current workflow existed only on `refac`. Because GitHub repository events read workflow definitions from the configured default branch, `main` was subsequently fast-forwarded to the identical `refac` commit without force or data loss before the final release-trigger pull request.

## 한국어

### 배경

PR #17은 `0.1.0`을 ready 상태로 선언하고 신뢰된 `refac` push 이후 게시하는 경로를 추가했습니다. 그러나 connector 기반 병합에서 push-triggered tag가 확인되지 않아, Pull Request head branch를 신뢰하지 않으면서 정확한 merge commit을 식별할 수 있는 별도의 신뢰된 GitHub 이벤트가 필요했습니다.

### 변경 내용

- `pull_request: closed` release 이벤트를 추가했습니다.
- Pull Request가 실제로 병합되고 base branch가 정확히 `refac`인 경우만 허용했습니다.
- 닫혔지만 병합되지 않은 Pull Request는 건너뛰도록 했습니다.
- 병합 후 검증과 게시에서 `pull_request.merge_commit_sha`를 checkout했습니다.
- Merge commit을 대상으로 dependency audit, Ruff, 전체 test suite, package build, 설치된 wheel smoke test, checksum을 다시 실행했습니다.
- 모든 release gate가 성공한 이후 publication job에만 `contents: write` 권한을 부여했습니다.
- Tag와 GitHub Release의 불변성을 유지했습니다.
- Workflow 회귀 테스트와 bilingual 신뢰 경계 문서를 추가했습니다.

### 검증 및 결과

Pull Request dry run, CI, Package, Ubuntu·macOS·Windows 테스트가 통과했습니다. 병합 후 저장소 branch를 확인한 결과 실제 설정된 기본 branch는 여전히 `main`이었고 최신 workflow는 `refac`에만 존재했습니다. GitHub 저장소 이벤트가 설정된 기본 branch의 workflow를 읽기 때문에, 최종 release-trigger Pull Request 전에 force나 데이터 손실 없이 `main`을 동일한 `refac` commit으로 fast-forward했습니다.
