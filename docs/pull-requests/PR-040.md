## English

### Context

PR #39 made installed launcher plugins executable through the same runtime as built-ins, but discovery diagnostics were concentrated in `modelctl launchers list`. The next working-first requirement is to make `modelctl doctor` answer whether installed plugins are healthy and to prove that external launchers inherit the existing compatibility safeguards rather than bypassing them.

### Implemented changes

- Extended `DoctorService` with one health check per external launcher discovery record.
- Report distribution origin, plugin ID, launcher contract version compatibility, and executable availability for loaded plugins.
- Keep unrelated broken, duplicate, incompatible, or availability-probe failures visible as warnings without disabling healthy launchers.
- Promote a failed currently selected plugin to an error in addition to the normal unknown-launcher error.
- Preserve the existing selected-launcher availability and provider/model compatibility checks.
- Document the distinction between discovery diagnostics (`modelctl launchers list`) and runtime health diagnostics (`modelctl doctor`).
- Document that discovered plugins use the same capability-driven launcher runtime as built-ins.

### Compatibility hardening

Regression tests now prove that discovered launcher plugins participate in:

- provider-aware launcher recommendation;
- preview-first compatibility remediation;
- strict compatibility enforcement;
- immutable `LaunchRequest` construction;
- native argument forwarding through `extra_args`;
- refusal to apply an unavailable recommended launcher.

### Status policy

- Loaded, contract-compatible, executable plugin: `OK`.
- Loaded compatible plugin with unavailable executable: `WARN`.
- Unrelated broken, duplicate, incompatible, or failed availability probe: `WARN`.
- Discovery failure for the currently selected launcher: `ERROR`.

This preserves discovery isolation while making the health impact explicit.

### Deferred work

- Static type-check enforcement at SDK, profile, and plugin boundaries.
- Evidence-driven profile portability only if real usage demonstrates a need.
- Final v0.3.0 documentation and readiness review.

## 한국어

### 배경

PR #39에서 설치된 launcher plugin을 built-in과 동일한 runtime으로 실행할 수 있게 했지만 discovery 진단은 주로 `modelctl launchers list`에 집중되어 있었습니다. 다음 working-first 요구사항은 `modelctl doctor`가 설치 plugin의 건강 상태를 판단하게 하고, 외부 launcher도 기존 호환성 안전장치를 우회하지 않는다는 것을 검증하는 것입니다.

### 구현 변경 사항

- `DoctorService`가 외부 launcher discovery record마다 health check를 생성하도록 확장했습니다.
- 정상 로드된 plugin에 대해 distribution origin, plugin ID, launcher contract version 호환성, executable availability를 표시합니다.
- 현재 선택과 무관한 broken, duplicate, incompatible plugin 또는 availability probe 실패는 정상 launcher를 막지 않으면서 warning으로 표시합니다.
- 현재 선택된 plugin 자체가 discovery에 실패하면 일반 unknown-launcher 오류와 함께 plugin 진단도 error로 승격합니다.
- 기존 선택 launcher availability 및 provider/model compatibility 검사를 유지합니다.
- Discovery 상태 확인용 `modelctl launchers list`와 runtime health 확인용 `modelctl doctor`의 역할 차이를 문서화했습니다.
- 탐색된 plugin이 built-in과 동일한 capability 기반 launcher runtime을 사용한다는 점을 문서화했습니다.

### 호환성 강화

회귀 테스트에서 외부 launcher plugin이 다음 기존 경로에 참여함을 검증합니다.

- provider-aware launcher recommendation
- preview-first compatibility remediation
- strict compatibility enforcement
- immutable `LaunchRequest` 생성
- `extra_args`를 통한 native 인자 전달
- 실행 불가능한 추천 launcher 적용 거부

### 상태 정책

- 정상 로드, contract 호환, executable 사용 가능: `OK`
- 정상 로드 및 contract 호환이나 executable 없음: `WARN`
- 현재 선택과 무관한 broken, duplicate, incompatible plugin 또는 availability probe 실패: `WARN`
- 현재 선택된 launcher의 discovery 실패: `ERROR`

따라서 discovery 격리 원칙을 유지하면서 실제 health 영향을 명확하게 표시합니다.
